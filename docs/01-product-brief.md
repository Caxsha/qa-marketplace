# QA Marketplace — Product Brief v2.1

## 1. Описание продукта
Веб-приложение интернет-магазина смешанного типа: товары (например, яйца, выпечка) и услуги
(например, оформление праздничного стола). Проект разрабатывается по реальному бизнес-сценарию
малого предприятия и используется автором как практический QA-проект и портфолио.

## 2. Цели проекта
- Практика полного цикла Manual QA на реальных, а не выдуманных требованиях.
- Освоение тестирования REST API и веб-интерфейса.
- Практика SQL и проверки целостности данных.
- Изучение автоматизации: Python + Pytest, Playwright.
- Формирование публичного QA-портфолио на GitHub.
- Побочная цель: рабочий инструмент, применимый в реальном небольшом бизнесе.

## 3. Целевая аудитория
- Незарегистрированные посетители (просмотр каталога).
- Зарегистрированные покупатели.
- Администратор — управление каталогом и заказами.

## 4. Границы проекта (Scope) — v1

Входит:
- Регистрация и авторизация.
- Каталог со смешанными позициями: товары (со складом) и услуги (со сроком выполнения).
- Поиск и фильтрация по категории, диапазону цен и типу позиции.
- Корзина.
- Оформление заказа с выбором способа получения: доставка или самовывоз.
- История заказов.
- REST API (JSON, под `/api`) отдельно от веб-страниц (HTML, под `/shop`), на общей бизнес-логике.

Не входит в v1:
- Онлайн-оплата (эквайринг, приём карт/QR прямо на сайте). Оплата — вручную,
  переводом по реквизитам после оформления заказа.
- Интеграция со службами доставки.
- Промокоды, бонусная система.
- Сложные роли и права доступа, кроме user/admin.
- Мобильное приложение (отдельный трек, стартует после стабилизации веб-версии).

## 5. Технологический подход
Веб-интерфейс и API разрабатываются с использованием AI-инструментов (vibe coding, PyCharm),
роль автора — проектирование требований, архитектуры, тестирование и автоматизация.
Это явно указывается в README репозитория.

## 6. Критерии успешности
- Основные пользовательские сценарии работают согласно требованиям.
- Подготовлена тестовая документация (test plan, test cases, чек-листы).
- API покрыт вручную (Postman) и автоматически (Pytest).
- Веб-интерфейс протестирован вручную и покрыт Playwright-тестами.
- Данные проверяемы напрямую через SQL/pgAdmin.
- Найденные дефекты оформлены как воспроизводимые баг-репорты.
- Проект имеет публичный GitHub-репозиторий с историей коммитов.

## 7. Юридический статус и оплата (бизнес-вопрос, не влияет на архитектуру v1)

Это открытый вопрос к заказчику, намеренно вынесенный за пределы технических требований —
он не должен определять архитектуру проекта на этом этапе.

- Если заказчик работает как самозанятый (НПД): разрешена продажа только товаров
  собственного производства. Выпечка подходит. Яйца подходят, только если это яйца
  от собственного хозяйства, а не закупленные оптом для перепродажи — совмещать
  свои и перекупленные товары в рамках НПД нельзя.
- Приём онлайн-оплаты картой/QR через эквайринг на сайте требует статуса ИП
  и расчётного счёта. Для самозанятого — только перевод на личную карту/по номеру
  телефона с оформлением чека в "Мой налог" на каждую продажу.
- Решение для v1 (уже отражено в Scope): сайт не обрабатывает оплату сам — после
  оформления заказа показываются реквизиты для перевода, оплата подтверждается вручную.

Нужно уточнить у заказчика: оформлен ли ИП/самозанятость, и являются ли яйца
собственным хозяйством или закупкой. До получения ответа считаем это бизнес-риском,
а не техническим требованием.
